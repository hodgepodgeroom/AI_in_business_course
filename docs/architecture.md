# Как устроена «Основа»

## Два сценария

Веб-сценарий начинается с готового списка материалов. React передаёт его API, который сохраняет заявку и ставит её в очередь. Python-обработчик забирает одну заявку, читает вложения, обращается к локальному серверу модели и ищет цены. Расчёт упаковок и сумм выполняет Python с Decimal. Интерфейс показывает результат и источники. Отдельный CLI начинает с ведомости работ и нормативов. Он использует предоставленные предложения из JSON и работает полностью офлайн. У сценариев разные входные данные и правила расчёта.

## Компоненты и хранение

| Компонент | Ответственность |
| --- | --- |
| apps/web/app | Форма, история, смета, уточнения, согласование и CSV. Кабинеты внутри интерфейса демонстрируют роли одного пользователя. |
| apps/web/lib/api.ts и domain.mjs | Проверка задания, переходы состояний, права владельца на заявки и файлы, CSV, выдача и завершение работы. |
| apps/web/local | Локальный HTTP-сервер принимает соединения на 127.0.0.1. SQLite хранит таблицы requests, files и worker. Содержимое вложений записывается в .local/uploads. |
| apps/web/worker и app/api | Размещаемый вариант получает идентификатор посетителя от доверенного шлюза ChatGPT Sites. Требуются привязки DB (D1), BUCKET (R2), секрет WORKER_SECRET и схема из drizzle/. Публиковать этот режим за шлюзом, подставляющим и проверяющим заголовки пользователя. |
| services/agent | agent.py ведёт очередь, attachments.py извлекает текст, model.py задаёт JSON-схемы, sources.py получает предложения, estimate.py считает корзины. |
| skills/prepare-construction-purchase | Скрипт procurement.py читает нормализованный JSON и экспортирует самостоятельный отчёт. Формат описан в references/data-contract.md внутри модуля. |

## API заявок

| Метод и путь | Результат |
| --- | --- |
| GET /api/bootstrap | До 80 последних заявок владельца и последний сигнал обработчика. |
| POST /api/files | Поле формы file, до 12 МиБ. Возвращает id вложения. |
| POST /api/requests | Поля text, city, address, deadline, необязательные title, budget, file_ids и submit. Ответ содержит id и state. |
| GET /api/requests/{id} | Исходные данные, результат, состояние и пояснение. |
| POST /api/requests/{id} | Запрошенный state и comment при согласовании. Сервер проверяет текущий статус. |
| GET /api/requests/{id}/csv | Таблица сметы с BOM, разделителем «;» и обработкой потенциальных формул. |
| POST /api/worker/claim | Атомарный захват заявки из очереди или сигнал занятости. Ответ содержит job, lease и метаданные вложений либо job=null. |
| POST /api/worker/update | По id и lease сохраняет прогресс или результат. Просроченная аренда получает 409. |
| GET /api/worker/file/{id} | Загрузка вложения доверенным обработчиком с общим ключом x-worker-secret. |

## Состояния и сбои

Сохранение создаёт draft, отправка создаёт queued. Обработчик переводит queued в processing. Результат с найденными позициями переходит в ready, отсутствие подбора — в needs_info, ошибка обработки — в failed. Из ready смета переходит в review. Для approved нужны комментарий, полный результат, выбранное предложение на каждой позиции и отсутствие вопросов. Повторный подбор из ready, review, failed или needs_info очищает предыдущий результат. Режим согласования имитирует решение в одном кабинете.

Два потребителя могут увидеть одну запись в очереди. Право на обработку получает первый, кому удалось условно изменить статус. Сервер выдаёт уникальную аренду. Обработчик обновляет её сигналами занятости. При следующем опросе свободным обработчиком заявки без активности более 20 минут переходят в failed. При отключении Mac необработанные queued-заявки сохраняются.

## Границы результата

Цена из поисковой выдачи отмечается как предварительная. Недостающие срок, доставка, количество и цена исключают полное подтверждение. Текущий извлекатель страниц консервативно сбрасывает точный складской остаток до неизвестного, поэтому найденные в интернете предложения обычно требуют ручной проверки и согласование может быть недоступно. Полный сценарий согласования проверяется на контролируемом подтверждённом результате. Модель работает с текстом, поддерживаются TXT, CSV, JSON, текстовый PDF, DOCX и XLSX. При загрузке изображения интерфейс сохраняет вложение, обработчик просит текст. Смета и источники относятся к моменту поиска.

## Решения при переносе

Из вложенного репозитория импортированы исходники кабинета, включая локальные изменения интерфейса. Расчётный модуль и обработчик восстановлены из исходного комплекта демо. Одинаковые копии расчётного ядра сведены к одному файлу. Генерируемые отчёты, npm-кеш, node_modules, база, приватные конфиги, старые идентификаторы запусков, приложение Ollama и веса создаются или подключаются отдельно. Первоначальная схема D1 используется и при создании локальной SQLite-базы.
